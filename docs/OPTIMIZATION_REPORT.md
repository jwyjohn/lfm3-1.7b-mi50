# LFM3-1.7B on MI50：从零开始的优化记录

这份报告记录把 [LiquidAI/LFM3-1.7B](https://huggingface.co/LiquidAI/LFM3-1.7B)（项目最早两步用的是同系列的 LFM3-VL-2B）跑在一张 2018 年的 AMD Radeon Instinct MI50（gfx906，官方已不再支持）上的全过程，时间是 2026-10-29 到 2026-11-08。每一步都写明做了什么、为什么做、效果多少。所有数字都是在这张卡上测的。

## 摘要

128k 上下文（约 127000 token 输入，输出 1024 token，单流，冷缓存）：

| 阶段 | 日期 | 首 token | decode tok/s | 输出是否可信 |
|---|---|---|---|---|
| 第一次跑通（vLLM，LFM3-VL-2B） | 10-29 | 238.4 s | 32 | 是 |
| 第一版 megakernel（LFM3-VL-2B） | 10-30 | 32.9 s | 132（单 token 7.55 ms） | **否，长上下文崩坏** |
| 修复精度后的基线 | 10-31 | 47.2 s | 166.8 | 是 |
| 重叠等待 | 10-31 | 46.5 s | 200.8 | 是 |
| Go + KFD 直连 | 11-02 | 46.0 s | 208.1 | 是 |
| DSpark（vLLM 上） | 11-04 | 44.7 s | 301.0 | 是，见[保真度](#gemv-的-x-改为-int8) |
| DSpark（Go） | 11-05 | 44.3 s | 307.4 | 同上 |
| prefill attention 换 int8 PV（Go） | 11-06 | 28.7 s | 307.4（decode 未改） | 是，长上下文 KL 略升，见[第 10 节](#10-第四阶段prefill-attention-翻倍11-06) |
| verify attention 一次读完 K/V（Go，当前版本） | 11-08 | 28.6 s | 423.7（同日旧版 305.4） | 是，attention 误差不变，见[第 11 节](#11-第五阶段decode-的-verify-attention11-07-到-11-08) |

decode 的后两行是 3 条流的中位数，受 τ 的混沌影响很大，读之前请先看[第 6 节](#6-为什么单条流的数字不能比)。

最终对比 vLLM（同一 kernel、同一策略）：

- **prefill、TTFT、热启动、采样路径 decode：** 每一档都更好，没有例外。
- **greedy decode 的 3 流中位数：** 每一档都更高（1k 974→1207，8k 532→954，32k 364→613，64k 413→450，128k 301→307）。
- **greedy decode 的 72 流总体：** 基本打平，均值 559→545（−2.5%），中位数 456→436（−4.4%）。差距来自落入循环的流；把这些流分开看，正常文本在每一档都快 5% 到 16%。
- **真实问答（MATH + GPQA，greedy）：** decode 高于 vLLM（MATH 616→639.5，GPQA 504.6→507.5），约为不用 draft 时的 2 倍（293 / 291），准确率没有下降。

可执行文件从 2.3 GB 降到 1.97 GB，同时多装了一个 drafter 模型。

之后 prefill attention 换成 int8 PV（第 10 节）：kernel 本身快 2.06 倍，128k 首 token 44.3 s → 28.7 s，32k 5.68 s → 4.62 s。代价是 softmax 概率从 fp16 变成 u8，60k 上下文对 HF fp32 的 KL 从 0.0171 升到 0.0251；`--exact-attention` 可以换回原来的 kernel。

## 1. 硬件

MI50 是 Vega 20：60 个 CU，每个 CU 4 个 SIMD，每个 SIMD 16 条车道。一个 wave 是 64 条车道同跑一条指令，4 拍发完。这里所有的 kernel 都按 60 个 block × 256 线程（4 个 wave）派发，一个 block 绑一个 CU。

下面的数字都是微基准实测（`benchmarks/` 里的数字另有说明）：

| 项目 | 实测 | 对设计的影响 |
|---|---|---|
| HBM2 持续读 | 约 785 GB/s，是理论 1024 GB/s 的 77%，和分块、在途深度、load 标志都无关，**原因未查清** | decode 的硬上限 |
| L2 | 8 MB 循环读 1605 GB/s，≥128 MB 约 790 GB/s，等效容量约 8 MB | 小矩阵的相位能超过 785 GB/s |
| 功耗 | 墙 178 W（`power1_cap_max` 也是 178 W）。只读内存就 174 W，sclk 从 1800 掉到约 1530 MHz | 计算受限的相位慢约 15% |
| 指令 | VALU 约 2.3 ns/条。`v_dot4`（4 组 int8 乘加）峰值约 47 TOPS，`v_dot2`（2 组 fp16）约 24.6 TFLOPS | int8 不只省内存，也快一倍 |
| LDS | 4 个 wave 同访时每次约 21 ns，相当于 9 条指令 | 128k 注意力的硬成本之一 |
| 每 CU 返回通道 | 约 16 B/clk | K/V 每 wave 只读一次，经 LDS 分发 |
| barrier | 计数器 + SMEM 轮询：空载 0.48 µs，内存满载 1.27 µs | 每轮一两百次 |

这张表就是 Roofline 模型的两条线：斜坡是内存带宽，屋顶是计算能力。

## 2. 模型和两种瓶颈

LFM3-1.7B：H = 2048，24 层（13 层卷积、6 层全注意力、5 层滑动窗口注意力），16 个 query head 共用 4 个 K/V head，head 维度 128。

推理分两段：

- **prefill**：把输入一次算完，矩阵乘矩阵（GEMM）。注意力是 O(T²)，128k 时约 45 秒里注意力占 32 秒，线性层 13 秒。这是**计算受限**。
- **decode**：一次一个 token，矩阵乘向量（GEMV）。每个 token 至少读 1.76 GB int8 权重，加上 128k 上下文时 0.81 GB 的 K/V，共 2.57 GB。按 785 GB/s 算至少 3.2 ms，所以**单 token 解码的物理上限是约 311 tok/s**。这是**内存受限**。

## 3. 第一阶段：跑起来，然后跑对（10-29 到 10-31）

### 起点

社区的 gfx906 分支让 ROCm、PyTorch 和 vLLM 还能在这张卡上跑。第一次跑通：127872 token 输入，首 token 238.36 秒，每 token 30.89 ms。和 3.2 ms 的上限差 10 倍，几乎全部花在调度上：每个算子一次 launch，每次都有 CPU 下发、信号等待、缓存操作。

### megakernel

把一个 token 的全部计算写进一个 kernel：一次 launch，60 个 block 同步走过每一个阶段，阶段之间用 grid barrier。CPU 不再插手。128k 单 token 降到 7.55 ms。

prefill 上，attention 换成寄存器分块的 Flash attention（不存 T×T 矩阵，只留 m、l、acc 三个累加量），线性层换成 W8A8 GEMM。128k 首 token 降到 32.9 秒。

### 快，但全错了

10-30 的数字很好看，但长上下文的输出是 `is is is is`。拿 HF fp32 当参考逐步查 KL，查出四个问题：

1. **RoPE 布局错误（主因）。** LFM3 的 partial RoPE 在 HF 中是 zero-tail 布局：旋转对是 (i, i+64)。vLLM 的实现是另一种。修正后原生路径的 KL 从 0.04–2.8 降到约 0。
2. **注意力的 P 按行量化成 int8。** 长上下文里概率很小，几乎全变 0，模拟 KL 4.8。
3. **W4 权重。** 模拟 KL 0.3–2.4。
4. **`QKVG` 常量写成 4112（应为 3088）。** 每层多读 1024 行权重；另外 decode 写 KV 记录时最后一个 head 的尾部和 scale 没写。

当时的高速数字建立在循环输出上，没有参考价值。这是整个项目最重要的一课：**评测必须包含正确性。**

### 精度方案

| 部分 | decode | prefill |
|---|---|---|
| 线性层权重 | int8，每 128 输入一个 scale | 同一份 |
| 线性层激活 | fp16 | int8，每 token 每 128 列一个 scale |
| KV cache | int8，每 token 每 head 一个 scale | 同左 |
| 注意力 | Q、K int8，P fp16，softmax fp32 | 同左 |

decode 对 HF fp32 的 KL 在 5 个提示上从 0.038–0.58 降到 0.0002–0.025。MATH-500 20 题 90%，20+20 题没有循环。代价是 128k prefill 从 3860 降到 2692 tok/s，decode 167 tok/s。这才是真实的基线。

### 把等待叠在一起

decode 每个 token 要过一两百个 barrier。以前是干等 barrier，barrier 过了再发 load、等内存。改成先报到（arrive），立刻发下一阶段的 load，再等，内存延迟就和 barrier 等待重叠了。128k decode 从 166.8 到 200.8 tok/s。其他改动：

| 改动 | 作用 |
|---|---|
| barrier 只等 LDS；K/V 和权重用 global load | flat load 让每次 LDS 等待都排空预取 |
| attention 一次处理 32 个 token，V 只转换一次 | 计算量下降 |
| K/V 的 load 分散到计算中间发 | 连续发 10 条 16B load 会阻塞，−0.1 ms |
| 采样合进 kernel | 省掉 argmax 和重复惩罚，约 175 µs/token，+4.2% |

prefill attention 同理：tile 循环里的 `__syncthreads()` 会等预取，改掉后从 12.3 到 12.6 TFLOPS，128k 2755 tok/s。

## 4. 第二阶段：脱掉外壳（11-02）

kernel 已经很快，慢的是它外面那一圈。这一阶段把 ROCm 用户态整个去掉，写了一个纯 Go 的 KFD 驱动（约 1100 行）：`ioctl` 分配显存和建队列，往环形队列写 64 字节的 AQL 包，写 doorbell。kernel 仍是 HIP，预编译成 code object 嵌进程序。怎么确认对：记录 ROCr 实际发出的 ioctl 和 AQL 包，逐字段比对。

启动从 38 秒到 5 秒。其他收获和坑：

- **省掉 L2 回写。** vLLM 路径上每个 token 结束时 system scope 回写整个 L2，最多 0.9 ms，只是为了让 CPU 读 4 字节的 token。改成 token 直接写进不经缓存的主机内存，fence 只用 agent scope，驱动每 token 只多约 0.04 ms。128k 从 200.5 到 208.1 tok/s。两边 kernel 耗时相同。
- **`h_old` 预取竞争。** 为了省时间，kernel 在等 barrier 前就预取残差。其他层都安全，但第 0 层的 h0 正是上一阶段由 block 0 写的，其他 block 可能读到上一个 token 的 embedding。在这个驱动下超过 16 个 block 就出现，ROCr 下同样的逐位比较测试却能通过。原因是时序。修复只改一行，kernel 时间 +0.6%。
- **页表竞争。** 打开 render 节点会启动内核里的异步页表更新。`ACQUIRE_VM` 在约 1 ms 内跟上时，KFD 写的 trap handler 页目录项会被覆盖。进程照常运行，直到某个 wave 被抢占，取不到 trap handler，队列卡死。debugfs 遍历页表才看到。`kfd.Open` 等 200 ms。
- **运行中会变的数据必须由 GPU 写。** CPU 从 BAR 写显存会绕过 L2，L2 里的旧值还在。

## 5. 第三阶段：DSpark（11-02 到 11-05）

### 思路

decode 的钱主要花在读权重。一次验证 M 个 token，权重也只读一遍：8k 上 M=1 每轮 3.73 ms，M≈4 只要 4.06 ms。小模型（drafter）先猜几个 token，大模型一次验证，提交相同的前缀加一个自己的 token：

> tok/s = τ / R，τ 是每轮提交的 token 数，R 是每轮耗时。

### Drafter

从 target 的第 2、6、12、18、23 层接出 5 路中间状态，RMS 后经 `fc` 压成上下文向量，投影成 3 层 drafter 注意力的 K/V，放进 4096 个位置的环（看最近 2048 个）。每轮输入 [anchor, mask × 8]，3 层注意力后过裁剪 LM head（最常用的 16384 个 token）和 Markov head（rank 256），confidence head 分数低于 −0.4 就停。

使用训练中途的权重 step 10260（2.6 亿参数）。回放的 τ：step 10260 均值 3.06、中位数 2.52；step 5130 均值 2.96、中位数 2.55。

### 写进 megakernel

draft 和 verify 每秒交替 200 多次，回 CPU 太贵，所以全写在一个 kernel 里，一次 launch 最多 32 轮。被拒的 token 不需要回滚：卷积历史放在按位置索引的环里，K/V 写在临时页，提交时才拷进 KV cache。

### 每轮耗时（8k，M≈3.8）

| 改动 | ms/轮 |
|---|---|
| commit、embed、Markov 改成多 block 并行 | 5.05 → 4.93 |
| **Layer 表走 SMEM**：barrier 的 L1 失效不影响标量缓存 | 4.93 → 4.77 |
| GEMV 行地址改为累加（每单元 65 条标量指令降到 18 条） | 4.77 → 4.69 |
| **GEMV 的 x 改为 int8**（`v_dot4`，指令少 25%，寄存器减半，溢出清零） | 4.69 → 4.47 |
| GEMV 每个 M 只留一份代码（I$ 有影响） | 4.47 → 4.40 |
| x 在 norm 写入端量化 | 4.40 → 4.34 |
| barrier 轮询走 SMEM，不被在途 load 卡住 | 4.34 → 4.27 |
| Q 每个 token 只算一次 | 4.26 → 4.20 |
| combine 每个任务一对 wave | 4.20 → 4.17 |
| `valid` 判断和标量运算移到少见路径 | 4.15 → 4.06 |

相同逻辑编译两次，每轮耗时可差 0.5–1%，所以小于 1% 的差异不可靠。

### 离 roofline 还有多远

| M≈3.8 | 每轮读取量 | 下限 | 实际 | 利用率 |
|---|---|---|---|---|
| 8k | 约 2.05 GB | 2.61 ms | 4.06 ms | 64% |
| 128k | 约 2.75 GB | 3.50 ms | 6.33 ms | 55% |

verify GEMV 已经 770 GB/s，是持续带宽的 98%。差距在内存闲置的相位：注意力、norm、barrier 合计约 1.45 ms，全轮约 38% 的时间内存基本空闲。draft 依赖上一轮 verify，这条链是串行的，能重叠的窗口很小。

### GEMV 的 x 改为 int8

这是全部工作里唯一一处用精度换速度的决定。固定 draft 为参考流，比较校验 logits 与 M=1 基线（8k，claudecode）：

| x 格式 | M | KL 均值 | top-1 一致（共 119） |
|---|---|---|---|
| fp16 | 1 / 4 / 7 | 0.00043 / 0.00044 / 0.00042 | 118 / 118 / 119 |
| int8（当前） | 1 / 4 / 7 | 0.00280 / 0.00277 / 0.00221 | 118 / 115 / 115 |

KL 约为 fp16 的 6 倍，top-1 翻转增加 1 到 4 处，都发生在第一名和第二名接近的位置。回退到 fp16 每轮慢 8–17%，并且需要 scratch 内存，而 Go 驱动没有。真实问答的准确率见[第 7 节](#7-结果)。

### 迁回 Go

Go 版本直接用同一个 kernel，只有三处改动：

1. **prefill**：v7 attention（`fast_exp2`），128k 以及 ≥32768 的 prompt 用 7680 token 的 chunk。
2. **State 增加 `stop_at` 和 `ckpt_slot`**：见下。
3. **上下文投影复用 prefill 的算子**：`rms`、GEMM、`kv_write`，不需要新 kernel。只在 tap 层多一次 rms，投影放到第一个 token 之后，不影响 TTFT。

**越过 block 边界。** vLLM 里 launch 必须停在 32 token 的 block 边界，因为卷积检查点只能存在那里，所以快到边界时 M 会被截短。Go 版本让 verify 越过边界，launch 过界后才停；过界不超过一轮，边界处的卷积状态由 kernel 收尾时从历史环里写一份。回放的增益不大：8k 均值 595.8→603.5（+1.3%），128k 282.0→283.6（+0.6%）。验证：用这些 K/V 和检查点热启动，和纯冷启动比 logprob，差距和无 draft 路径同量级。

**体积。**

| 内容 | 原始 | 存储 | 说明 |
|---|---|---|---|
| int8 权重 + drafter | 1655 MiB | 1539 MiB | Huffman 只省 7%：接近随机噪声 |
| embedding | 500 MiB | 332 MiB | 按字节面分开编码，省 34%：BF16 转 fp16 后低 3 位全是 0 |
| LM head | 260 MiB | 0 | 就是量化后的 embedding，启动时现算 |
| prefill 布局 | 约 1.5 GB | 0 | 同一批 int8 的不同排列，启动时现算 |
| drafter 的 head 裁剪、k/v 投影 | 约 45 MiB | 0 | 量化是逐行独立的，从已有的行直接抄 |

启动从约 5 秒变成 7.5 秒，内存峰值约 7.3 GB（含文件映射）。

## 6. 为什么单条流的数字不能比

这是这一阶段最反直觉的发现。

verify 的数值和 M 有关：M 不同，注意力的分组不同，浮点取整就不同。近似打平的位置于是可能换一个 token，后面的文本和 τ 就全都不一样了。

实例：加一条「连续两次没接受就只猜一个 token」的规则，回放里基本中性（8k 均值 −0.2%，128k 均值 +1%），但在基准上：

| 档位 | 没有这条规则 | 有这条规则 |
|---|---|---|
| 1k | 1207 | 706 |
| 8k | 954 | 406 |
| 32k | 613 | 415 |
| 64k | 450 | 412 |
| 128k | 307 | 493 |

这些评测 prompt 是截断的 agent 轨迹，又带 `ignore_eos`，模型跑过自然结束点后常常掉进循环（`SIGNATURE SIGNATURE ...`、`c9c9c9...`）。这种循环在 vLLM 和无 draft 路径上都有。好猜的循环能到 1300 tok/s，难猜的只有 250。哪条流掉进哪种循环，就是抽签。

所以我们：

- 用 **R（每轮耗时）** 比 kernel，它不受序列影响。
- 用**固定序列回放**（`sim_conf.py`）比策略。
- 用**多条流 + 把循环流分开**看 Go 和 vLLM 的差别。
- 3 流中位数继续汇报，但**不用它挑配置**。上面这条规则因此没有采用：回放说中性，就不增加复杂度。

为了排除 drafter 的移植错误，还比较了逐轮 draft：同一 prompt、同一前缀，72 个对齐的轮次里 60 个的 M 和 draft 完全相同，其余差在低置信的尾部 draft。

## 9. 还没解决的

- **785 GB/s。** 持续读只有理论值的 77%，原因没查清。
- **178 W。** 突破要改 powerplay 或降压，是硬件层面的决定，没有动。prefill attention 现在也受它限制：持续运行时频率在 1556 和 1711 MHz 之间切换。
- **u8 的 softmax 概率。** prefill attention 的提速建立在它之上，60k 的 KL 升高约 47%。试过的两种修正（分母也用量化值、32 key 一块）都没有带来净收益；需要 fp16 精度时用 `--exact-attention`。
- **int8 x 的保真度。** 回退需要驱动先支持 scratch。
- **drafter 权重还在训练。** 新权重到了要重新回放策略：`./build.sh model <新权重目录>` 即可重建。
- **只测了这一张卡。** 没有长时间稳定性测试，最长的一次是准确率评测。
- **默认 temperature 是 0.1。** 模型的默认采样参数不走 DSpark，约 260 tok/s。要 DSpark 需 `temperature: 0`。这和 vLLM 行为一致。

## 10. 第四阶段：prefill attention 翻倍（11-06）

128k 预填充的 44.3 s 里，attention 占 32.6 s（6 个全注意力层 × 18 个 7680 token 的 chunk，加 5 个滑动窗口层）。目标是让这一步至少快一倍。所有 kernel 都先在 vLLM 开发环境里用同一套 ROCm 7.2.4 工具链编成 code object，通过 HIP module API 加载测试，测的就是 Go 会加载的字节；再迁回 Go。

### 为什么必须换掉 fp16 PV

旧 kernel（16 token × 4 head 一个 block，QK 用 int8 `v_dot4`，PV 用 fp16 `v_dot2`）每个 score 要 32 条 QK 点积加 64 条 PV 点积。即使 VALU 100% 忙，128k 的下限也约 13.5 s，翻倍要做到这个下限的 93%，不现实。PV 也换成 `v_dot4`，点积数降到 64 条，才有空间。

P 不能按整行量化，那正是第一阶段长上下文崩坏的原因之一（"快，但全错了"）。新方案按**每行、每 64 个 key 的 tile** 量化：P' = p × V scale，相对 tile 内最大的 P' 量化成 u8（0–255，就近取偶），V 加 128 变成无符号，`v_dot4_u32_u8` 累加到 u32，最后减去 128 × ΣP'。每个 tile 有自己的尺度，远处的小概率 tile 不会被一个大值压成 0。

### 一步步变快（128k 的 attention 合计，旧 kernel 32.6 s）

| 版本 | 改动 | 128k 合计 |
|---|---|---|
| v8 | int8 PV；512 线程、32 token × 4 head 一个 block，每个 SIMD 2 个 wave；`v_exp_f32`；最大值懒更新（超过 2^8 才 rescale） | 约 23 s（按单点比例估算），但寄存器溢出到 scratch，不能用 |
| v9 | 全展开（`sched_barrier` 控住加载）；mask 只在边界 tile 做；P' 最大值的规约用带 DPP 的 `v_max` 四行交错 | 约 19.5 s（按单点比例估算） |
| v14 | QK 的 int32 部分和从 1.5·2^23 的位模式开始累加，读回来直接是 float，每组一次 fma；K 提前两列取；KV 步长写成常量 | 17.0 s |
| v30 | wave 0–3 先做 tile s 的 QK+softmax 再做 PV，wave 4–7 先做 tile s−1 的 PV 再做 tile s 的 QK+softmax；每个 SIMD 一个 wave 在算 QK、另一个在算 PV，LDS 请求错开；K/V 双缓冲，每个 tile 2 个 barrier | 16.6 s |
| v41 | `s_setprio`：QK 2、PV 1、softmax 0，让 LDS 密集的 QK 先发射 | **15.9 s（2.06 倍）** |

另加了沿 key 的拆分（grid z 加 combine kernel），给 2048 token 的 chunk 和 prompt 末尾的短 chunk 用：128k 的最后一块（512 token，上下文 130560）从 55.7 ms 降到 21.4 ms。

v30 让 LDS 等待减少 65%（计数器 SQ_WAIT_INST_LDS），VALU 忙碌率约 81%。这张卡在功耗墙（178 W）上：持续运行时频率在 1556 和 1711 MHz 之间切换，单点测量（有空隙）比连续跑一个 prompt 快约 8%，表里的数字都是连续跑的。

### 编译器的坑

512 线程的 block 把 VGPR 限在 128，驱动又没有 scratch，下面几处每一处都会造成大量溢出：

- barrier 之前算好的值被挪到 barrier 之后的使用处，导致所有加载过的操作数都活到那里（383 个寄存器溢出）。用空的 `asm volatile("" : "+v"(x))` 把 logits 和累加器钉在原处。
- 两个分支里一模一样的 barrier 内联汇编，会让编译器把两组 wave 的循环合并。两组的 barrier 字符串不同。
- 一对 8 字节加载的两半在两个条件下分别存到 LDS，被合并成一次存储，而且存的是错的那一半（V scale 读成了 V 的数据）。改成每个线程只加载一个 dword 到一个变量。
- 立即数偏移的 `buffer_load ... lds` 会把偏移同时加到 LDS 地址上，编译器设 M0 时没扣掉（最终没用 LDS DMA）。

`kernels/build.sh` 现在会检查每个 code object：有 VGPR 溢出或 private segment 就构建失败。

### 精度

用 HF fp32 模型模拟 kernel 的量化（int8 K/V、每 32 维一组的 int8 Q、各自的 P 量化），比较最后 192 个位置的下一 token 分布：

| | 16k | 60k 会话 A | 60k 会话 B | 60k 均值 |
|---|---|---|---|---|
| 仅 int8 KV | 0.00012 / 100% | 0.0307 / 94.8% | | |
| 旧 kernel（fp16 P） | 0.00025 / 100% | 0.0290 / 94.3% | 0.0051 / 97.9% | 0.0171 / 96.1% |
| 新 kernel（u8 P） | 0.00025 / 99.5% | 0.0434 / 88.5% | 0.0067 / 97.4% | 0.0251 / 93.0% |

（KL / top-1 一致率。）16k 看不出差别；60k 的 KL 升高约 47%，但离第一阶段的崩坏（KL 4.8）差得很远。输出逐位确定（prefill 三次 logits 完全相同）。需要旧精度时加 `--exact-attention`，它运行原来的 kernel（`kernels/prefill_attn_exact.hip`），128k 首 token 回到 44.4 s。

## 11. 第五阶段：decode 的 verify attention（11-07 到 11-08）

目标是 32k 800、128k 600 tok/s（`cmd/bench` 的 3 流中位数），重点放在 decode 的 flash attention 上；drafter 权重和 draft 方式不变，每轮 draft 数上限和置信度阈值可以重新调。起点是同一天重测的上一版：32k 425.8，128k 305.4。**两个目标都没有达到**，结果是 32k 687.9、128k 423.7，原因见本节最后。

### 每轮的时间花在哪

kernel 里本来就有 `trace_mark` 打点，这次接到了 Go 这边：`LFM3_DS_TRACE=<block>` 把这个 block 的打点记下来，请求结束时按相位汇总到服务日志。第一版把打点直接写进主机内存（GTT），每个打点都是一次跨 PCIe 的写，后面 barrier 的 `vmcnt(0)` 要等它，每轮多出约 40%；改成写 VRAM、每次 launch 后拷回主机。打点缓冲区每次 launch 只放得下约 4090 个点，一轮约 500 个，所以开 trace 时每次 launch 最多跑 4 轮。

128k、M≈3、上一版：attention 相关（6 个全注意力层、5 个滑动窗口层的 attention，加上每层的 query 和 combine 相位）约 2.1 ms，GEMV 约 2.4 ms（已在带宽附近），norm 和 barrier 等待约 0.6 ms，每轮 6.0 ms。32k 时 attention 相关约 0.85 ms。

### 起点：页划分的 v2

之前留下一个没提交的 `attention_v2`：每次迭代一个 32 key 的页，一个 wave 负责一个 KV head，K 和转成 fp16 的 V 在 LDS 里只放一次，每遍最多 4 个 token；block 按页划分，新 K/V 页算作 block 0 的第一页。128k、M = 4 每层 345 µs（旧的 `attention_pass` 是 452 µs），但 M = 5 到 8 要两遍，每遍都把 K/V 读一次（M = 8 是 680 µs）。

它有一个竞争：为了和 barrier 等待重叠，第一页的 load 在等 query 相位之后的 barrier **之前**就发出，而新 K/V 正是其他 block 在 query 相位写的。没有上下文页、第一页就是新 K/V 页的 split 会读到旧数据：256 key 的滑动窗口层上，M ≤ 2 时 block 0 每层都是这种情况。fp64 对照里，M = 2 的最大误差是 1.7e-3（正常 3.8e-4）。现在新 K/V 页一律在 barrier 之后才发。

### v3：一次 K/V 读取覆盖全部待验证 token

M 最多 8（7 个 draft 加 anchor）。v2 的 QK lane 是（query head j，8 个 key 之一，64 维的一半），每条 lane 存每个 token 64 维的 query，8 个 token 要 128 个 VGPR，加上 PV 的 64 个累加器就放不下了（megakernel 已经用满 256 个 VGPR，驱动没有 scratch）。

`attention_v3<NT>`（NT = 4 或 8）的 QK lane 改成（query head j，4 个 key 之一，4 个 32 维组之一）：每条 lane 每个 token 只存 32 维（正好一个 query scale 组），8 个 token 64 个 VGPR。同一个 key 的 4 条 lane 的部分分数要求和：寄存器 r 存的是 token `(r & ~3) | ((r & 3) ^ dq)`，于是 reduce-scatter 每 4 个 token 只要 3 个 DPP 运算，做完 lane dq 正好拥有 token dq 和 4 + dq。PV lane 和 v2 一样（head j，8 维），P 经 LDS 交换，放在 K 的位置（K 那时已经用完），一个 wave 的 LDS 仍是 13 KB。

其余改动：

| 改动 | 作用 |
|---|---|
| 页的 block id 一次读进 VGPR，循环里用 `v_readlane` | 原来每页一个标量 load，它的 `lgkmcnt(0)` 会把正在进行的 LDS 写也一起等完 |
| 先写 K 和 scale，再转换 V | 第一批 K 读取只排在 K 的写后面 |
| int8 V 转 fp16 用 SDWA 的 `v_cvt_f16_i16`（符号扩展字节） | 每个 dword 2 条指令，原来是 perm + 减偏置约 3 条；v2 也用上了 |
| 伙伴 lane 的整数和在转换时就做 DPP（`v_cvt_f32_i32_dpp`） | 省掉单独的 `v_mov_b32_dpp` |

每页每个 wave 的指令数：NT = 4 时 1166（v2 1212），M = 8 时 2096（v2 两遍 2424）。M = 3 仍走 `attention_v2<3>`，比把 v3<4> 补一个空 token 快。

### 功耗墙

M = 1 已接近内存下限（128k 每层 138 MB，176 µs）；之后每多一个 token，128k 每层多约 55 µs，大约是每页每 token 235 条指令的发射时间。持续运行时的频率说明了原因（M = 4，128k）：

| 版本 | 每层 | sclk | 功耗 |
|---|---|---|---|
| v3 | 345.8 µs | 1354 MHz | 175 W |
| 不发页的 load（读旧数据） | 269.0 µs | 1538 MHz | 179 W |
| 不做 PV | 266.6 µs | 1333 MHz | 179 W |
| 不做 QK 点积 | 291.6 µs | 1383 MHz | 178 W |

全部顶在 178 W。K/V 读取本身就占掉一部分功耗预算，把频率压到约 1350 MHz，于是计算慢了。所以能省的只有每个 token 的指令数：fp16 PV 每页每 token 至少 128 条 `v_dot2`，QK 64 条 `v_dot4`，现在是 235 条左右，剩下的空间不大。PV 改用 int8（像 prefill 那样）能省约四分之一，但会降低 decode 每个 token 的 attention 精度，没有做。

### 策略

verify 变便宜后，长上下文多 draft 的代价变了。用 18 条流（每个 prompt 去掉开头 16·v 个 token，v = 0..5）比较每轮最多 3 个和 7 个 draft，均值 / 中位数 tok/s：

|---|---|---|
| 32k | 627 / 532 | 668 / 611 |
| 48k | 477 / 463 | 509 / 481 |
| 64k | 468 / 462 | 436 / 431 |
| 128k | 406 / 412 | 380 / 331 |

### 为什么没有达到 800 / 600

tok/s = τ / R。128k 的中位数流 τ 约 2.0 到 2.4：要 600 tok/s，R 得降到 3.3 到 4.0 ms，而这一轮要读的字节（1.76 GB 权重、约 0.2 GB drafter、0.83 GB K/V）按 785 GB/s 算就要 3.6 ms，现在是 5.5 ms，其中全注意力层约 1.35 ms、GEMV 约 2.4 ms。即使全注意力层只剩内存时间、其余不变，R 约 5.2 ms，128k 也只有 440 左右。32k 的中位数流 τ 约 2 到 3.3，要 800 需要 R 在 2.5 到 4.1 ms，现在 4.5 到 5.2 ms，attention 相关只占 0.8 到 1.0 ms。剩下的差距在 τ（drafter 本身，不能改）和 attention 之外的相位（GEMV、norm、barrier、drafter 的串行链）。
